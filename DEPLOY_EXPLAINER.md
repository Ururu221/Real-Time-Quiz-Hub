# Як працює деплой Real-Time Quiz Hub

Пояснення всього шляху коду: від «пишу локально» до «працює на проді».
Писалося для джуна — простими словами, без зайвої теорії.

---

## 🛡️ Шпаргалка для захисту (що сказати комісії)

1. **Застосунок пакується в Docker-образ** — один контейнер з ASP.NET Core застосунком, який всередині слухає порт 8080.
2. **Деплоєм керує інструмент `simpled`** — він читає файл `appspec.yaml` (опис застосунку: які сервіси, змінні, секрети) і за ним генерує конфіг для сервера.
3. **CI/CD на GitHub Actions, розбитий на дві стадії:** *release* (зібрати образ + опублікувати) і *deploy* (викотити на сервер).
4. **Release запускається автоматично** при пуші в `main`, якщо змінився `appspec.yaml`. Він збирає образ, пушить його в GitHub Container Registry (ghcr.io) і створює GitHub Release з «бандлом».
5. **Deploy запускається вручную** з окремого репозиторію деплойментів — там лежить конфіг усіх проектів організації. Він завантажує бандл і через `rsync + ssh` розкладає все на сервер.
6. **Версіонування через `version` в `appspec.yaml`** — підняв версію, запушив → новий реліз. Не підняв → релізу нема (це навмисно).
7. **Образ один раз збирається, далі тільки переноситься** — той самий образ, що протестований, їде на прод. Нічого не перезбирається на сервері.

> Якщо спитають «а яка роль simpled?» — це обгортка, яка з простого `appspec.yaml` робить усю рутину: тегує образ, пушить, готує деплой-конфіг під Docker Swarm. Щоб не писати це руками для кожного проекту.

## Компоненти по черзі

### 1. `justfile` — «зручні скорочення команд»

`just` — це як `make`, тільки простіше. У файлі описані «рецепти» (команди), які ти запускаєш як `just <ім'я>`. Щоб не пам'ятати довгі docker-команди напам'ять.

| Команда | Що робить | Коли юзаєш |
|---------|-----------|------------|
| `just build` | Збирає Docker-образ застосунку через `docker buildx` і тегує його `plaingood/quiz-hub-app:latest` | Це **головна** команда — її викликає CI перед публікацією. Локально майже не треба |
| `just run` | `docker compose up --build -d` — піднімає локально app + базу даних у фоні | Коли хочеш потестити все локально як на проді |
| `just down` | Зупиняє і прибирає локальні контейнери | Закінчив тестити |
| `just logs` | Показує логи застосунку наживо | Дебаг — подивитись що пише app |
| `just migrate` | Накочує EF Core міграції (структуру таблиць) на базу | Після зміни моделей / першого запуску |

**Важливе:** рецепт `build` — це контракт із `simpled`. Образ мусить зватися рівно так, як написано в `appspec.yaml` (`plaingood/quiz-hub-app`), бо потім simpled шукає саме `...:latest`, щоб його перетегувати й запушити.

---

### 2. `appspec.yaml` — «паспорт застосунку для simpled»

Це найважливіший файл деплою. simpled його читає й розуміє: *що це за застосунок, з чого складається, що йому треба для роботи*. Сам застосунок цей файл не використовує — це суто для деплою.

Що в ньому описано:

```
name: real-time-quiz-hub        # ім'я застосунку (мусить збігатись у репо деплойментів)
version: 1.0.0                   # версія → стає тегом образу. Підняв версію = новий реліз

environment:                     # змінні оточення
  external: Logging__LogLevel... # є дефолт, але середовище може перезаписати
  internal: ASPNETCORE_*         # фіксовані, однакові скрізь (порт 8080, Production)

secrets:                         # чутливі дані — НЕ зберігаються тут, тільки оголошуються
  db_connection_string           #   рядок підключення до БД (з паролем)
  jwt_secret                     #   ключ для підпису JWT-токенів

app_services:
  app:                           # єдиний сервіс застосунку
    type: public                 #   public = доступний ззовні через ingress (HTTP)
    image: plaingood/quiz-hub-app#   ім'я образу (без тегу — simpled додасть версію)
    environment: [$all]          #   передати сервісу всі змінні згори
    secrets:                     #   секрети інжектяться як env-змінні:
      db_connection_string  →  ConnectionStrings__DefaultConnection
      jwt_secret            →  JwtSettings__Secret
    ports: ["8080:8080"]         #   зовні:всередині
```

**Ключові ідеї для розуміння:**
- **Секрети тут лише *оголошені*, без значень.** Значення підставляються на деплої з GitHub Secrets. Так пароль не лежить у git.
- **`db` (база) тут НЕМАЄ.** Бо база — це окрема інфраструктура на сервері, а не частина застосунку. Застосунок просто отримує рядок підключення до неї через секрет.
- **`image` без тегу.** simpled сам додасть `:1.0.0` (з поля `version`). Префікс `plaingood` на проді розгортається в `ghcr.io/plaingoodtech/`.

---

### 3. `Dockerfile` — «як зібрати образ»

Двостадійна збірка (multi-stage) — класика для .NET:

1. **Стадія `build`** (важкий SDK-образ): копіює код, робить `dotnet restore` + `dotnet publish -c Release`. На виході — зібраний застосунок у `/app/publish`.
2. **Стадія `final`** (легкий runtime-образ `aspnet:8.0`): бере тільки готові файли з першої стадії. SDK у фінальний образ не потрапляє → образ маленький.

Результат: контейнер слухає `8080`, запускається через `dotnet RealTimeQuizHub.dll`. Усередині вже є і фронтенд (`wwwroot`), і дані (`questions.json`) — бо `publish` їх включає.

> Навіщо два етапи: щоб у фінальному образі не тягати весь .NET SDK (це сотні МБ). Збираємо «жирним», запускаємо «худим».

---

### 4. `docker-compose.yml` — «локальний прод у мініатюрі»

Це **тільки для локальної розробки**, на проді не використовується. Піднімає два контейнери:
- `db` — PostgreSQL 16 (з healthcheck, порт 5432 відкритий назовні щоб накотити міграції)
- `app` — наш застосунок (збирається з Dockerfile), порт 8080

Сенс: одна команда `just run` (=`docker compose up`) — і в тебе локально крутиться те саме, що буде на проді. Зручно тестити перед пушем.

---

### 5. `.github/workflows/release.yml` — «автоматична публікація»

Це CI, який спрацьовує **сам**, коли ти пушиш у `main` зміну в `appspec.yaml` (або в самому цьому файлі). Покроково:

```
1. Тригер: push у main, де змінився appspec.yaml
2. Ставить just і simpled на раннер (чисту віртуалку GitHub)
3. Checkout — викачує твій код
4. Логіниться в ghcr.io (GitHub Container Registry) під твоїм акаунтом
5. `just build` → збирає образ plaingood/quiz-hub-app:latest
6. `simpled app-bundle create`:
     • перетегує образ → ghcr.io/plaingoodtech/quiz-hub-app:1.0.0
     • пушить образ у registry (--push-images)
     • створює GitHub Release з бандлом (--upload-bundle-to github-release)
```

**Що таке «бандл»:** по суті це запакований `appspec.yaml` (опис застосунку). Образ у нього не входить — образ живе окремо в registry. Бандл = «інструкція як розгорнути версію 1.0.0», образ = «сам застосунок».

Чому тригер тільки на `appspec.yaml`: реліз = свідома дія. Поправив код, але не підняв версію → релізу нема. Підняв `version` в appspec → поїхав новий реліз.

---

### 6. `.github/workflows/dotnet-desktop.yml` — «перевірка коду» (CI, не деплой)

Окремий workflow, не плутати з деплоєм. Запускається на кожен push і PR у `main`. Робить `dotnet restore → build → test` у двох конфігураціях (Debug і Release). Це просто «чи код взагалі компілюється і чи проходять тести». До деплою прямого стосунку не має — це захист якості.

---

### 7. Deploy-workflow (в окремому репо деплойментів)

Цей файл **не в цьому репозиторії** — він лежить у репо, що керує деплоєм усіх проектів організації. Запускається **вручну** (workflow_dispatch), ти вводиш версію. Що робить:

```
1. Ставить simpled + SSH-ключ до сервера
2. `simpled prepare-deployment real_time_quiz_hub_prod --app-version X`
     • качає бандл версії X з GitHub Release
     • підставляє секрети (з GitHub Secrets того репо)
     • генерує готовий docker-deploy/ конфіг під Docker Swarm
3. rsync — копіює docker-deploy/ на сервер
4. ssh + ./deploy.sh — сервер піднімає/оновлює контейнери
```

Тобто публікація (release) і викочування (deploy) — **розділені**. Спочатку версія публікується, потім ти окремо вирішуєш коли її викотити на прод.

## 🗺️ Загальна схема pipeline

```
                          ЛОКАЛЬНО (ти)
  ┌──────────────────────────────────────────────────────────┐
  │  пишеш код → just run (тестиш локально: app + db)         │
  │           → піднімаєш version в appspec.yaml              │
  │           → git push origin main                          │
  └───────────────────────────┬──────────────────────────────┘
                              │
                              ▼
            СТАДІЯ 1: RELEASE (автоматично, GitHub Actions)
  ┌──────────────────────────────────────────────────────────┐
  │  release.yml спрацьовує (бо змінився appspec.yaml)        │
  │   1. just build → збирає Docker-образ                     │
  │   2. simpled app-bundle create:                          │
  │        • пушить образ → ghcr.io/plaingoodtech/...:1.0.0   │
  │        • створює GitHub Release з бандлом                 │
  └───────────────────────────┬──────────────────────────────┘
                              │   (образ у registry + бандл у Release)
                              ▼
        СТАДІЯ 2: DEPLOY (вручну, репо деплойментів)
  ┌──────────────────────────────────────────────────────────┐
  │  запускаєш deploy-quiz-hub.yml, вводиш version = 1.0.0    │
  │   1. simpled prepare-deployment → качає бандл, підставляє │
  │      секрети, генерує docker-deploy/                      │
  │   2. rsync docker-deploy/ → на сервер                     │
  │   3. ssh ./deploy.sh → сервер тягне образ і піднімає      │
  │      контейнер                                            │
  └───────────────────────────┬──────────────────────────────┘
                              │
                              ▼
                        СЕРВЕР (прод)
  ┌──────────────────────────────────────────────────────────┐
  │  Docker Swarm піднімає контейнер app (порт 8080)         │
  │  ingress (reverse proxy) маршрутизує домен → контейнер    │
  │  Let's Encrypt видає TLS-сертифікат                       │
  │  + потрібен DNS-запис: quizhub.plaingood.tech → IP        │
  └──────────────────────────────────────────────────────────┘
                              │
                              ▼
              https://quizhub.plaingood.tech 🎉
```

### Одним реченням
Ти пушиш зміну версії → GitHub сам збирає образ і публікує реліз → ти вручну запускаєш деплой → сервер качає образ і піднімає контейнер → сайт працює на домені.

## Найчастіші питання (на випадок каверзних)

- **«Чому реліз і деплой окремо?»** Щоб контролювати *коли* версія потрапляє на прод. Зібрати можна одне, а викотити пізніше або зовсім іншу версію.
- **«Де зберігаються паролі?»** У GitHub Secrets (репо деплойментів). У git і в appspec.yaml їх нема — там лише імена секретів.
- **«Що як змінив код, але не версію?»** Релізу не буде — тригер дивиться тільки на `appspec.yaml`. Це фіча, не баг.
- **«Навіщо simpled, чому не просто docker?»** Щоб не писати руками тегування/пуш/генерацію конфігів для кожного з ~7 проектів. Один `appspec.yaml` — і все автоматично.
- **«Образ перезбирається на сервері?»** Ні. Збирається раз у CI, на прод їде той самий протестований образ із registry.
```
